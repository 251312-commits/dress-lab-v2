# DRESS LAB V2

기존 [DRESS LAB](https://github.com/251312-commits/dress-lab)의 **대화 중심 마법 메이크오버 샵 게임** 기획과 의상·콘텐츠 관리 원칙을 계승하되, 캐릭터의 파츠 구조와 렌더링을 새롭게 만드는 프로젝트다. **기획의 계승은 이전 버전의 코드를 그대로 이식한다는 뜻이 아니다.**

> **문서 구분:** 아래 '계승할 기획'과 'V1 시스템 참고'는 향후 설계 기준이다. V2에서 이미 작동하는 기능은 문서 뒷부분의 **V2 현재 구현 상태**만을 기준으로 판단한다. V1 기록의 현재형 설명은 **V1의 구현 상태**를 가리킨다.

> **출처:** [DRESS LAB README](https://github.com/251312-commits/dress-lab/blob/main/README.md) · README에서 연결한 [메이크오버 게임 기획 메모](https://github.com/251312-commits/dress-lab/blob/main/docs/GAME_DESIGN_NOTES.md). 이관한 핵심 원문은 기본적으로 문구와 규칙을 유지했고, 제목 단계 및 V1/V2 구분 표시만 정리했다.

## 계승할 게임 기획 — 원문 발췌

대화 중심의 **마법 메이크오버 샵 게임**으로 확장 중이다.

### 1. 게임의 핵심

- 플레이어는 마법의 메이크오버 샵에서 손님을 맞이하고 기본 관리, 외형 변경, 코디, 대화를 진행한다.
- **매 방문마다 여러 요소를 확률적으로 조합해 새로운 클라이언트를 생성한다.** 정해진 고정 캐릭터 몇 명의 스토리를 진행하는 게임이 아니다.
- 가장 중요한 재미는 **의상·색·전체 코디를 바꿀 때 손님이 실시간으로 하는 반응**과 선택형 스몰토크이다. 긴 고정 스토리나 점수 맞히기는 우선순위가 낮다.
- '추구미'는 정답처럼 처음부터 보여주지 않는다. 플레이어는 손님의 말과 반응으로 취향을 추론하고, 취향 밖의 스타일도 제안할 수 있다.
- 손님은 처음의 취향을 반드시 고수하지 않는다. 성격·대화·경험에 따라 의외의 스타일을 발견할 수 있다.

### 2. 클라이언트 생성 및 첫 화면

#### 생성 데이터 (내부 정보 포함)

- 이름, 초기 외모(피부색·체형·눈/눈동자·머리 등), 초기 의상·메이크업.
- **성격 자질 풀**에서 여러 자질을 확률적으로 조합. 심즈식 자질 시스템 구상(예: 수줍음, 사교적, 직설적, 까칠함, 신중함, 모험적, 감상적 등). 자질 목록·개수·상충 규칙은 미확정.
- **선호/비선호 해시태그** 및 전체 스타일의 선호 경향(추구미). 초기에는 비공개.
- **방문 이유 풀**에서 짧은 이유를 확률적으로 선택. 예: '새로운 룩을 보여주고 싶어요', '친구가 데려왔어요'.
- 필요하면 개인적 기억 또는 특성을 무작위로 부여한다. 방문 이유는 장식 문구에 그치지 않고 성격·기억·대사 조건에 연결한다.
- 모든 요소를 무작위로 뽑되, 앞뒤가 모순되는 조합에는 제약/가중치를 둘 수 있다(구체 규칙 미정).

#### 최초 제공되는 '클라이언트 파일'

- **짧고 간결하게**: 초기 외모/이미지, 이름, **한 줄짜리 방문 이유** 정도만 노출한다.
- 성격 자질·취향 태그·개인적 기억 등은 내부에 보유하되 처음부터 공개하지 않는다.
- 상세한 인물 전기, 정답 스타일표, 선호 수치를 첫 파일에 보여주지 않는다.
- 마법의 샵이므로 이후 플레이 중 피부·체형·눈·머리 등 외형도 변경 가능하다.

### 3. 의상 스타일 데이터

#### 3.1 파라미터 — 5개 축

각 의상에 **-5 ~ +5** 정수 척도의 특성을 부여한다.

| 축 | -5 방향 | +5 방향 |
|---|---|---|
| 격식 | 매우 캐주얼 | 매우 격식적 |
| 화려 | 수수·절제 | 화려·장식적 |
| 편안 | 조이거나 활동이 제한되는 인상 | 느슨하거나 편안한 인상 |
| 파격 | 관습적·익숙함 | 실험적·독창적 |
| 노출 | 신체를 많이 가림 | 노출이 많음 |

**핵심 규칙:** 파라미터는 개별 의상 하나의 세부 수치로 대사를 분기하기 위한 것이 아니다. **현재 착용한 의상들의 값을 합산하여 전체 코디의 특성을 판단**하고, 합계가 속한 **몇 개의 범위/구간**에 따라 전체 스타일을 분류한다. 개별 정수 조합의 모든 경우의 수를 다루지 않는다.

- 실제 구간 경계는 의상 수·종류 분포를 본 후 확정한다.
- 반지/액세서리 등 아이템 수에 의해 합계가 과도하게 치우치지 않도록 부위별 비중·중복 보정 등은 추후 검토한다. **단순 합산을 기본 구상으로 유지**한다.
- 즉각적인 대사 발동의 주역은 파라미터가 아니라 아래 **해시태그**이다.

#### 3.2 해시태그 — 4개 범주

1. **장르/스타일 계열**: 예) #고딕 #로맨틱 #펑크 #프레피 #스트리트 #발레코어
2. **소재**: 예) #레이스 #데님 #가죽 #벨벳 #니트
3. **분위기**: 예) #몽환적 #우아한 #귀여운 #퇴폐적 #중성적
4. **현재 선택한 색**: 예) #버건디 #인디핑크 #아이보리 #코발트블루

- 장르·소재·분위기는 의상 속성으로 부여할 수 있다(복수 가능).
- 색상 태그는 의상의 고정 특성이 아니라 **현재 선택된 RGB 색상**에서 판정해 동적으로 바꾼다.
- 색상은 넓은 '빨강 계열/파랑 계열' 태그를 겉에 추가하지 않고 **세부 색상 영역**으로 분류하려는 구상이다. RGB 입력을 HSV/HSL 등으로 해석해 영역을 판정하는 구체적 경계는 아직 정하지 않았다.
- **해시태그와 손님의 선호/비선호가 실제 실시간 반응을 주도**한다. 파라미터는 코디 전체의 보조 맥락으로 쓴다.

### 4. 손님의 반응과 대화

#### 의상 변경 시 말풍선

- 플레이어가 옷 또는 색을 바꿀 때 관련된 해시태그·선호/비선호·성격 자질·기억을 보고 반응 대사를 선택한다.
- 필요할 때 전체 코디의 파라미터 합산 구간도 참고한다.
- 동일한 #레이스 옷이라도 좋아하는 손님, 싫어하는 손님, 그 옷과 관련된 기억이 있는 손님은 다르게 말한다.
- 성격 자질은 특히 **말투, 감정 표현, 새 스타일을 받아들이는 태도**를 바꾼다.
- 각 변경에 대한 짧은 코멘트와, 특별 조건에서 열리는 긴 대사를 구분할 수 있다. 반복 방지 규칙은 추후 설계한다.

#### 대화 버튼 / 스몰토크

- 별도 '말 걸기' 버튼에서 플레이어의 대사·질문 **후보 중 하나를 선택**한다.
- 손님은 선택지 및 현재 상태에 맞춰 응답한다.
- 대화는 취향을 알아내거나 추구미와 다른 스타일에 대한 새 반응을 끌어내는 수단이다.
- 선택 이력/이전에 선호·거절한 의상 등은 방문 중 일관되게 기억해야 한다.
- '선호 발견'을 UI에 얼마나 공개할지, 관계도/점수/엔딩을 둘지는 **미확정**.

### 5. 백스토리보다 가벼운 '기억/특성' 우선

- 방대한 고정 캐릭터의 백스토리는 **필수 요소가 아니다**. 당장은 생략하거나 최소화 가능하다.
- 클라이언트 생성 시 **현재 게임에서 사용 가능한 의상 몇 개를 무작위 선택**해 개인적 의미(추억, 동경, 거부감 등)를 부여하는 방안을 우선 검토한다.
- 특정 옷 또는 태그와 연결된 기억은 조건부 특수 대사를 연다.
- 방문 이유도 이러한 성격·기억에 영향을 줄 수 있다. 예: '친구가 데려왔어요' → 자발적이지 않은 방문에 대한 반응.
- 핵심은 방대한 서사보다 **새로 생성된 손님이 자신만의 말과 반응을 가진 것처럼 느껴지는 것**이다.

### 7. 대사 제작 원칙

- **모든 대사를 사람이 직접 작성할 계획은 없다.** AI로 대사 데이터를 대량 생성하고, 사람이 검수·최종 수정한다.
- 초기 권장안은 **개발 시점의 일괄 생성 → 파일에 저장 → 조건에 따라 출력**이다. 플레이 중 실시간 AI API 호출은 필수 조건이 아니며, 적용 여부도 정하지 않았다.
- 모든 수치·성격·태그 조합에 일대일 대사를 만들지 않는다. 범용 반응, 태그 선호/비선호, 성격 변주, 기억에 따른 특수 대사 등으로 분리한다.
- 대사에는 **텍스트뿐 아니라 발동 조건(태그, 상황, 선호 여부, 성격 조건, 우선순위)**을 함께 기록한다.
- AI 초안의 중복, 어색함, 설정 모순, 같은 손님의 발화 일관성을 자동 검사하고 샘플 검수한 뒤 확장한다.
- 대사와 이미지 데이터는 코드와 분리하여 신규 콘텐츠를 추가할 수 있도록 설계한다.

### 9. 다음 기획 작업

1. **5개 파라미터의 의미**와 전체 코디 합산 구간의 초안 마련.
2. **태그 사전** 정리: 장르·소재·분위기·세부 색상 영역 및 중복 표기 규칙.
3. **성격 자질 풀/조합 규칙**과 선호·비선호의 랜덤 생성 규칙 작성.
4. **방문 이유 풀** 작성, 이유별 성격·기억 영향 정의.
5. **대사 조건 스키마와 우선순위**를 정한 후 AI 초안 생성·검수 실험.
6. 의상 카탈로그·더미 PNG 구축 → 실물 PNG로 점진적 교체.
7. 샵의 방 구성·대화 UI·케어/메이크업 흐름을 검증.

#### 기획상 미결정 사항

- 파라미터 합계의 실제 경계값, 아이템 종류별 비중.
- 캐릭터의 자질 수·모순 조합 처리·취향 변화 규칙.
- 해시태그 전체 목록과 세부 RGB 색상 분류 임곗값.
- 기억용 의상 개수와 개별 아이템/태그 단위 중 무엇을 우선할지.
- AI 생성 대사의 품질 관리 기준과 데이터 형식.
- 클라이언트 관계도, 최종 평가·엔딩, 재방문 시스템의 필요 여부.

## 기존 DRESS LAB의 4개 방·케어 UI 방향

> 다음 내용은 V1 README의 UI 기록이다. V2도 네 방 버튼을 유지하지만, **현재는 마법룸에서만 실제 체형 슬라이더가 연결되어 있고 나머지 방은 UI 시안 또는 자리표시자**다. V1의 배경 슬라이드·케어 기능을 그대로 이식한 것은 아니다.

### 모바일 방 이동 UI (시안)

- 화면 하단의 **접수실 · 케어룸 · 마법 거울실 · 드레스룸** 버튼으로 방을 전환한다.
- 방 전환 시 배경이 좌우로 미끄러진다. **거울실과 드레스룸에서는 인형이 약간 왼쪽에 배치되고 오른쪽에 기존 세로형 편집 사이드바가 자동 표시**된다.
- 거울실 오른쪽에는 기존 **체형 · 피부톤 · 얼굴** 탭, 드레스룸 오른쪽에는 기존 **옷장 · 색상 조절** UI가 표시된다. 별도의 새 편집 기능을 만든 것이 아니라 기존 UI를 재배치한 것이다.
- **케어룸** 상단은 방 이동 버튼과 같은 **심볼+이름** 탭(페이셜·헤어·릴랙세이션)이다. 캐릭터 앞쪽 하단에는 그림 아이콘 도구 3개가 놓인 **선반**이 있다. 텍스트 단계 안내와 기존 헤어 관리 패널은 케어룸 화면에서 숨기지만 원래 코드는 보존한다. 도구를 세 종류 모두 시연 선택하면 카탈로그 자리표시자 아이콘이 나타난다. 접수실은 사이드바 없이 전체 화면을 사용한다.
- 모바일 세로 화면뿐 아니라 터치형 가로 화면에서도 오른쪽 편집 패널이 보이도록 구성했다.
- 접수실은 안내 화면만 있는 자리표시자다. 방 배경은 외부 이미지가 아닌 임시 CSS 삽화다.
- 모바일 PNG 저장 버튼은 드레스룸에서 보이며, PC에서는 기존 편집 패널도 계속 표시된다.
- UI 구성 파일: `app/room-navigation.css`, `app/room-navigation.js`, `app/care-room.css`, `app/care-room.js`. 기존 인형 렌더링과 의상 파일 규칙은 수정하지 않았다.
- 케어룸은 **UI 시연만 가능**하다. 선반의 도구는 조작 기능이 없는 심볼 플레이스홀더이며, 선택 시 완료 표시만 바뀐다. 첫 방문과 재방문은 카테고리마다 내부 상태와 도구 구성이 다르다. 새로고침하면 시연 상태가 초기화된다. 필요한 제작 자료는 [케어룸 에셋 체크리스트](docs/CARE_ROOM_ASSET_CHECKLIST.md)에 정리했다.

## 기존 DRESS LAB의 의상 콘텐츠 시스템 — V2 이식 검토용

> 다음 세 절은 **V1에서 작동하는 업로드·의상 레이어 시스템의 원문**이다. V2에는 아직 `editor.html`, `clothes/`, `item.json` 로더, 자동 목록 생성 및 확장 의상 렌더링이 없다. 아래 경로와 이미지 규격은 V1 전용이며, V2 구현 완료를 뜻하지 않는다.

### 의상 추가: 코드 수정 불필요

1. 투명 배경 PNG를 만든다. **모든 이미지에 인형과 같은 좌표 원점을 사용**한다.
2. editor.html에서 의상 ID, 이름, 분류, 기본 색, 캔버스 규격을 선택한다.
3. 앞/뒤 PNG 여러 개를 선택하고 각 이미지의 인형 앞/뒤, 순서(숫자가 클수록 나중에 합성)를 지정한다.
4. **item.json 다운로드**를 누른다.
5. GitHub에서 clothes/영문-ID/ 폴더에 원본 PNG와 item.json을 모두 올린다. 폴더명과 JSON의 id가 일치해야 한다.
6. main에 반영하면 Actions가 자동으로 data/wardrobe.json을 생성해 배포하고 새 옷을 인식한다. 이미지와 설정은 GitHub 저장소에 남는다.

예: clothes/rose-evening-dress/back.png, front.png, item.json. 설정 예시는 clothes/_example/item.example.json을 참고한다. 이름이 _로 시작하는 폴더는 예시용으로 무시한다.

### 이미지 캔버스 규격

| 규격 | PNG 크기 | 기본 인형 이미지에 대응하는 영역 | 사용처 |
|---|---|---|---|
| standard | **252 × 730 px** | x=0~252, y=0~730 | 기본 옷, 상의, 하의 |
| expanded | **504 × 900 px** | x=126~378, y=0~730 | 풍성한 드레스, 넓은 치마, 아래로 긴 자락 |

확장 규격에서 인형의 중심선은 **x=252**이다. 기존 252×730 이미지의 원점은 **확장 캔버스의 (126, 0)** 으로 이동한다. 즉, 기존 의상과 같은 위치에 그린 다음 양옆으로 126px씩, 아래로 170px을 더 쓸 수 있다. 이미지의 실제 그림 위치를 자동으로 맞춰 주지는 않는다.

제작 가이드는 guides/standard-guide.svg, guides/expanded-guide.svg에 있다. **가이드 격자는 의상 PNG에 병합하지 않는다.**

확장 의상 선택 시 미리보기/저장 화면의 캔버스 크기도 넓어진다. 기본 인형과 일반 의상은 기존 체형 변형 엔진을 사용한다. 확장 의상의 추가 면적은 기존 체형 변형을 바탕으로 가로 띠 단위로 변형한다. 극단적인 체형 설정에서는 가장자리의 세부 변형이 기존 좁은 의상과 완전히 동일하지 않을 수 있다.

### 여러 레이어를 한 벌로 묶기

한 벌의 parts에 여러 PNG를 지정할 수 있다. 인형 뒤에 보이는 자락은 plane: back, 몸 앞에 보이는 부분은 plane: front로 설정한다. order는 같은 면과 의상 분류 안에서 나중에 합성되는 순서를 결정한다. 해당 의상을 입거나 벗으면 **모든 PNG가 함께 처리**된다.

의상 분류 group: upper, top, vest, outer, dress, skirt, lower, socks, shoes, neck, waistAccessory.

## V1과 V2를 구분해야 하는 기술적 차이

| 항목 | DRESS LAB (V1) | DRESS LAB V2 현재 상태 |
|---|---|---|
| 캐릭터 표현 | 기존 인형 이미지와 체형 변형 엔진 | 같은 크기의 투명 PNG 17개를 겹쳐 기본 캐릭터 렌더링 |
| 기준 이미지 규격 | standard 252×730 / expanded 504×900 | `base/` 1206×2622. V2 의상 규격은 아직 설계·확정되지 않음 |
| 레이어 순서 | 의상 `parts.order` 값이 클수록 나중에 합성되는 V1 의상 규칙 | `base/` 파츠는 **파일명 숫자가 작을수록 위에 표시**되는 별도 규칙 |
| 의상 등록 | `editor.html` → `item.json` → `clothes/ID/` → 빌드된 목록 | 자동 의상 등록 기능 아직 없음. 향후 V2의 파츠 구조에 맞춰 재설계 필요 |
| 방 전환 | 배경 좌우 슬라이드와 방별 편집 패널 연결 | 네 방을 선택하면 오른쪽 패널이 방에 맞게 전환됨. 마법룸 체형 기능 작동, 나머지 방은 UI 시안 |
| 케어·메이크업·대화 | V1 일부 UI 시안, 게임 로직 미구현 | V2도 현재 UI 배치 단계. 게임 로직 미구현 |

**V2 신규 개발 원칙:** 인형의 파츠와 의상 이미지는 가능한 한 동일한 좌표계에 놓고, 체형을 구현할 때 과도한 전체 이미지 왜곡을 되풀이하지 않는다. 의상 이미지와 메타데이터를 코드에서 분리하고, 한 벌에 여러 앞/뒤 레이어를 연결하는 V1의 운영 장점은 유지할 방향으로 검토한다. 구체적인 V2 의상 스키마와 변형 방식은 미확정이다.

## V2 현재 구현 상태·실행 방법

아래 내용은 **실제 V2 저장소** 기준이다. 위의 V1 참고 사양과 혼동하지 않는다.

### 작동 방식

- `base/` 안에 동일한 픽셀 크기와 좌표로 제작된 **투명 배경 PNG** 파일을 넣는다.
- 파일명 앞의 숫자가 레이어 순서다. **숫자가 작을수록 앞에 표시된다.** 예: `01-Head.PNG`는 `17-Hand(R).PNG` 위에 놓인다.
- `Full.PNG`는 관절 위치 참고 자료이므로 **캐릭터 합성에서 제외**한다.
- **기본 자세(모든 관절 0°)**에서는 각 파츠를 `(0, 0)`에 그대로 겹쳐 그린다. `rig/rig.json`의 관절값을 바꾸면 원본 이미지를 왜곡하지 않고, 파츠 전체를 회전축 중심으로 이동·회전한다.
- 합성 이미지를 별도 제목·테두리·여백 없이 게임 화면 전체에 표시한다.
- 원본 파츠의 좌표를 유지하면서 아트보드를 화면에 최대한 크게 맞춘다. 화면과 원본 비율이 같으면 화면 전체를 채우며, 비율이 다르면 이미지가 잘리지 않도록 남는 부분을 흰색으로 둔다.
- UI는 `ui/layout.css`와 `ui/layout.js`에서 별도로 관리하고, 인형 그림은 기존 `index.html` 렌더러로 합성한다. 두 레이어 모두 **1206 × 2622** 기준 좌표를 사용한다.
- 사이트를 열 때 공개 GitHub API를 통해 `base/` 폴더의 숫자로 시작하는 PNG 파일을 찾아 자동 반영한다. API 접근이 불가능하면 `index.html`에 기록한 초기 17개 파츠를 사용한다.

### UI 배치 미리보기

2026-11-22 스케치 기준으로 다음 영역을 배치했다.

- **왼쪽 위:** 말풍선 대화창
- **오른쪽:** 드레스룸은 실제 작동하는 HSB 색상환·슬라이더와 의상 UI 시안, **마법룸은 위에서부터 `체형 → 피부톤 → 얼굴` 탭**. 현재 `체형`에는 검은 선 위주의 13개 실제 슬라이더가 있으며, `피부톤`에는 독립 HSB 컬러휠·채도/명도 조절·HEX 미리보기가 있고, `얼굴`은 아직 안내 화면이다. 두 방 모두 인형 원본 좌표를 유지한다.
- **아래쪽:** 대화하기, 완료 버튼과 접수실·케어룸·마법룸·드레스룸 버튼

좌표와 버튼 외형은 `ui/layout.css`, 버튼 구성과 UI 전용 상태는 `ui/layout.js`에서 수정한다. 파츠 PNG의 위치나 레이어 순서는 변경하지 않는다.

**메인 게임은 아직 UI 개발 단계다.** 방 버튼을 누르면 방별 오른쪽 패널이 달라지며, **마법룸 `체형` 탭의 슬라이더 13개만 실제 인형 변형에 연결**되어 있다. `피부톤` 탭에서도 드레스룸과 별개로 색조·채도·밝기를 선택하고 HEX 코드를 복사할 수 있으며, `얼굴` 탭은 아직 편집 기능을 제공하지 않는다. 드레스룸의 HSB 색상환은 터치·마우스 드래그로 색조(바깥 고리)와 채도·밝기(안쪽 마름모)를 선택할 수 있다. H/S/B 슬라이더·1단계 증감 버튼·HEX 표시가 함께 갱신되고, HEX 표시를 누르면 코드를 복사한다. 의상 색상은 `dresslab:color-change` 이벤트와 `window.DressLabColorWheel.getColor()/setColor()/setHex()`로 제공한다. 피부톤 색상은 별개의 `dresslab:skin-color-change` 이벤트 및 `window.DressLabSkinColorWheel.getColor()/setColor()/setHex()`로 제공한다. 피부톤 기본 미리보기는 `#E8BEAD`이며 인형의 실제 색상은 아직 바뀌지 않는다. 다만 실제 의상/피부 PNG의 재색칠, 의상 착용, 대화 선택지, 케어·완료 진행은 아직 연결되지 않았다. **관절 테스트 모드에서는 포즈와 동작 애니메이션을 별도로 시험할 수 있다.**

### 관절 시스템 기초 (구현됨 · 개발용 테스트)

- `base/Full.PNG`의 **11개 파란 원 중심**을 좌표로 추출해 `rig/rig.json`에 기록했다.
- 몸통 1개, 어깨·팔꿈치·손목 각 2개, 고관절·무릎 각 2개로 구성한다. **머리·목에는 별도 회전축이 없다.**

- 17개 원본 PNG의 파일명·레이어 순서와 0° 기본 자세를 보존한다.
- **[관절 테스트 열기](https://251312-commits.github.io/dress-lab-v2/?rig=1)** : 개발용 슬라이더, 축 표시, `Full.PNG` 반투명 참고, 팔 들기·손 흔들기, 포즈 JSON 저장.

## 자동 idle · 탄성 포즈 애니메이션

### 바스트 — 상단 고정

`03-Bust.PNG`를 다른 토르소 파츠와 분리해 크기 조절한다. 위쪽 부착선(원본의 첫 비투명 행, 약 y=1010px)은 **고정**하고 하단으로 크기를 키우거나 줄인다. 세로 크기는 슬라이더 증감량을 100% 반영하고, 가로 너비도 아래쪽으로 갈수록 증감량의 100%까지 반영한다. **최상단 부착선의 위치와 너비는 고정**한다. 기존 상체 폭 조절과 동시에 사용할 수 있다.

### 상하체 비율 — 연결부와 관절 함께 이동

V1의 82~118% 범위를 사용하되 변형 원리는 변경했다. **어깨선과 발끝 위치를 고정**하고, 비율이 증가하면 몸통(어깨~골반)이 길어지면서 다리(골반~발끝)가 상대적으로 짧아진다. 감소하면 반대다. 골반·무릎·팔꿈치·손목과 몸통의 회전축, 각 신체 파츠도 **같은 세로 좌표 변환**을 따라가므로 관절 연결을 유지한다. 초기화 시 모든 이미지·회전축이 원래 위치로 돌아간다.

### 기존 변형 기능과 연결

- 목 길이는 목/상체가 겹치는 y≈970px 부근을 고정하고 머리를 함께 이동한다. 머리와 목에 새 회전 관절을 만들지 않는다.
- 상체 폭은 `UpperTorso`·`Bust`와 양팔 위치를 연결하고, 허리는 `TorsoJoint`와 양쪽 토르소의 연결 너비를 공유한다.
- 골반·허벅지 연결부에서는 **허벅지 굵기 변화량의 70%**, 무릎 위·아래에서는 허벅지·종아리 변화량의 **각각 30%**를 공유한다.
- 팔 길이를 바꾸면 팔꿈치·손목과 손 이미지가 함께 이동한다. 손 크기는 별도로 조절하며 손목 근처는 팔 두께에 맞춰 보간한다.

구현 파일: `rig/body-shape.js`(원본 기준 변형 및 회전축 이동), `ui/magic-room.js`(슬라이더), `ui/layout.css`(13개 항목 고정형 배치), `rig/body-shape-debug.js`(개발용 패널). 아직 의상 변형이나 게임 이벤트와의 연결은 미구현이다. 큰 체형 변화에서 외곽선·명암과 회전 중 관절 겹침은 별도 시각 확인이 필요하다.

### 바스트 명암 레이어 설계 메모

현재 바스트 PNG에도 자체 음영이 있어, 이번 변경에서는 추가 명암을 덧씌우지 않았다. 향후 `BustShadow` 투명 레이어를 별도로 두고 가슴 아래·중앙부 그림자의 불투명도만 바스트 크기에 맞춰 미세 조정하면 형태의 볼륨을 표현하기 쉽다. 전체 바스트를 균일하게 어둡게 하는 방식은 피하는 편이 자연스럽다.
